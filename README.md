# Satellite Security Testbed

This repository contains a multi-component simulation environment for satellite cybersecurity experiments. The testbed coordinates a Manager process, a React WebApp, an orbital/environment simulator, a cyber-attack executor, and an operational spacecraft/ground-station simulator.

The code is designed so each component can run on a separate computer, while development and demos can run from one machine if each daemon is started in its own terminal.

## Components

- **Manager** (`src/Manager`) - central orchestrator. It starts the WebSocket server for the WebApp, sends startup messages to the component daemons, accepts component connections, sends preparation data, and relays execution updates.
- **Orbital computer / data conversion** (`src/dataConv`) - computes satellite position, solar intensity, and magnetic field data from the TLE and simulation time. It can drive NI DAQ outputs and optional map/video displays.
- **Cyber computer** (`src/cyber`) - receives the attack schedule from the Manager and launches attack classes when their configured occurrence minute is reached.
- **Operational computer** (`src/Operational/rubysat`) - generates and executes a command timeline, communicates with COSMOS/RubySat, forwards command and telemetry updates to the Manager, and can receive Raspberry Pi metrics.
- **Web application** (`WebApp/TestBedWebApp`) - React/Vite interface for TLE upload, simulation configuration, attack selection, live status, telemetry graphs, map display, and command logs.
- **mongo** (`mongo`) - local MongoDB data directory used when Manager Mongo writing is enabled.

## Main Runtime Flow

1. Start the three component daemons: orbital, cyber, and operational.
2. Start the Manager with `python ManagerServer.py`.
3. Start the WebApp with `npm run dev`.
4. In the WebApp, configure the TLE, start epoch time, duration, number of runs, optional attacks, and run options such as Mongo saving or command-file reuse.
5. When the WebApp sends `stage: "start"`, the Manager contacts each daemon and sends `["main", manager_ip]`.
6. Each daemon spawns its component `main.py` or manager script, then the component connects back to the Manager on `manager_PORT`.
7. Components request their preparation data with `stage: "prep"`.
8. During execution, components share updates with `stage: "execution"` and receive the current simulation state back from the Manager.
9. The Manager forwards satellite state, command events, and graph updates to the WebApp over WebSocket.
10. When the configured duration ends, the Manager sends a simulation-complete message. The WebApp returns to the configuration screen and shows a closeable completion popup so another run can be started cleanly.

## WebApp Run Options

The simulation configuration screen includes a few run-time options that are sent to the Manager with the start message:

- **Save simulation data to MongoDB** - enables Manager writes for that run. Leave it off when you do not want new simulation records written to MongoDB.
- **Manager command file name** - name used when saving or loading generated command timelines on the Manager side. If the name is empty, the Manager uses `latest_commands.txt`.
- **Save generated file** - saves the command timeline generated by the operational component into `src/Manager/saved_command_files/`.
- **Load saved file** - uploads the selected command timeline from the WebApp machine to the Manager, then sends it to the operational component so the same scheduled commands can be reused.

The browser file picker cannot be forced to open a specific directory, so choose the saved command file manually. In the normal one-machine setup, saved command files are in:

```text
src/Manager/saved_command_files/
```

That folder is ignored by Git because it contains local run artifacts.

## Deployment Options

The intended deployment uses multiple machines:

| Machine | Code | Role |
| --- | --- | --- |
| Manager/WebApp | `src/Manager`, `WebApp/TestBedWebApp` | Orchestration and browser UI |
| Orbital computer | `src/dataConv` | Environment and DAQ output |
| Cyber computer | `src/cyber` | Attack scheduling and execution |
| Operational computer | `src/Operational/rubysat` | Spacecraft/COSMOS command and telemetry flow |

For local development, run all processes on one computer and keep the configured IP addresses pointed to that host.

## Prerequisites

- Python 3.12 or a compatible Python 3 environment
- Node.js and npm
- A Python virtual environment or conda environment for the Python dependencies
- MongoDB, only if Manager persistence is enabled
- NI DAQ drivers/hardware for non-demo orbital output
- COSMOS/RubySat environment for the operational component

## Installation

Clone the repository:

```bash
git clone https://github.com/texydo/satellite_security_testbed.git
cd satellite_security_testbed
```

Install Python dependencies for the subsystems you will run:

```bash
pip install -r src/dataConv/requirements.txt
pip install -r src/cyber/requirements.txt
pip install -r src/Operational/requirements.txt
```

Install WebApp dependencies:

```bash
cd WebApp/TestBedWebApp
npm install
```

## Configuration Checklist

Before running across multiple computers, update the placeholder values in:

- `src/Manager/config/manager_config.ini`
  - `manager_comp_ip`
  - `dataConv_comp_IP`
  - `operational_comp_IP`
  - `cyber_comp_IP`
  - `manager_PORT`
  - `daemon_server_PORT_ENV`
  - `daemon_server_PORT_OP`
  - `daemon_server_PORT_CYBER`
  - `WEBAPP_COM.webapp_com_PORT`
- `src/dataConv/dataConv_config.ini`
  - daemon host/port
  - Manager communication port
  - DAQ channel names
  - solar and magnetic calibration values
  - demo/full-cycle video paths
- `src/cyber/cyber/cyber_config.ini`
  - attack target IP and port
  - cyber daemon host and port
- `src/Operational/rubysat/sim_config.ini`
  - COSMOS command/telemetry ports
  - COSMOS directory path
  - Manager communication port
  - operational daemon host/port
  - Raspberry Pi metrics port

On Linux or any case-sensitive filesystem, keep the data conversion config filename aligned with the code paths. The repository file is `dataConv_config.ini`, while some code references `DataConv_config.ini`.

## Running the System

Start each daemon in its own terminal:

```bash
# Orbital computer
cd src/dataConv
python daemon_server.py

# Cyber computer
cd src/cyber
python daemon_server.py

# Operational computer
cd src/Operational/rubysat
python daemon_server.py
```

Start the Manager:

```bash
cd src/Manager
python ManagerServer.py
```

Start the WebApp:

```bash
cd WebApp/TestBedWebApp
npm run dev
```

The WebApp development server normally opens at `http://localhost:5173`. The frontend currently connects to the Manager WebSocket at `ws://127.0.0.1:8765`.
