# Manager Subsystem

The Manager is the central orchestration component of the Satellite Security Testbed. It runs two threads:

- a WebSocket server for the React WebApp
- a simulation execution loop that coordinates orbital, operational, and cyber components

Entry point:

```bash
cd src/Manager
python ManagerServer.py
```

## Files

| Path | Purpose |
| --- | --- |
| `ManagerServer.py` | Starts the WebSocket thread and simulation execution thread |
| `simHandlers/webAppComHandler.py` | Receives WebApp messages and sends UI updates over WebSocket |
| `simHandlers/simExecutionHandler.py` | Starts component daemons, accepts component connections, handles prep/execution loops |
| `utils/ManagerClass.py` | Stores simulation state, graph buffers, satellite state, MongoDB settings, and component update handling |
| `utils/ProcessDataClass.py` | Builds satellite state snapshots from TLE and epoch time |
| `utils/utils.py` | MsgPack socket helpers and config access helpers |
| `config/manager_config.ini` | Manager, component, MongoDB, demo, and WebApp communication settings |

## Runtime Flow

1. `ManagerServer.py` creates two `queue.Queue` objects:
   - WebApp to simulation thread
   - simulation thread to WebApp
2. `startWsServer()` opens the WebSocket endpoint on `localhost:8765`.
3. `handle_simulation_execution()` waits for the WebApp `stage: "start"` message.
4. The Manager sends `["main", manager_ip]` to each daemon.
5. Components connect back to `manager_comp_ip:manager_PORT`.
6. Each component sends a `stage: "prep"` request.
7. The Manager sends role-specific preparation data.
8. After all expected components finish prep, the Manager resets the simulation clock and sends `stage: "simulationStarted"` to the WebApp.
9. During execution, components share updates and the Manager responds with current simulation state.
10. Satellite position, command updates, and graph data are placed on the WebApp queue.
11. When the configured duration finishes, the Manager sends `stage: "simulationComplete"` to the WebApp, closes current component sockets, and waits for the next WebApp `start` message instead of requiring a Manager restart.

## WebApp Messages

The WebApp currently sends JSON messages over WebSocket. The Manager accepts string messages with `ast.literal_eval()` and binary MsgPack messages with `msgpack.unpackb()`.

Common incoming stages:

| Stage | Meaning |
| --- | --- |
| `start` | Start a simulation with TLE, duration, attacks, playback speed, and demo flag |
| `stop` | Stop the running simulation and close component sockets |
| `pause` | Pause the execution loop until `resume` is received |
| `resume` | Resume after pause |
| `setRequestedGraphs` | Request graph fields, sent by the frontend after start |
| `setAttackFactor` | Update attack factor stored on `ManagerServerData` |

The `start` message can also include:

| Field | Meaning |
| --- | --- |
| `saveToMongo` | Enables MongoDB writes for this run. If false, live updates still work but run data is not written to MongoDB. |
| `saveCommandFile` | Save the command timeline generated by the operational component. |
| `loadCommandFile` | Forward an uploaded command timeline to the operational component instead of asking it to generate a new one. |
| `commandFileName` | Local file name used under `saved_command_files`; the Manager sanitizes the value before writing or reading. |
| `commandFileContent` | Text uploaded by the WebApp file picker when loading a saved command file. |

Common outgoing payloads:

- satellite state snapshots containing `Time`, latitude/longitude, altitude, solar intensity, magnetic field, and lighting state
- command objects containing `command` and `timeCommandSent`
- graph dictionaries keyed by telemetry field, such as `EPS_BATTERY_TOTAL_VOLTAGE`
- `stage: "simulationComplete"` when the run reaches the configured duration

## Component Preparation Payloads

The Manager sends a different `stage: "prep"` payload to each component:

| Component | Data sent |
| --- | --- |
| `orbital` | `tle`, `time`, solar intensity `min`/`max`, `demo` |
| `operational` | `time`, `tle`, `night_probability`, simulation duration in seconds, command/attack log flags, optional loaded command-file content |
| `cyber` | `time`, `tle`, configured `attacks` |

The WebApp duration is entered in minutes. The Manager converts it to seconds before sending it to the operational component.

## Command File Save/Load

Generated command timelines can be saved on the Manager computer in:

```text
src/Manager/saved_command_files/
```

When `saveCommandFile` is true, the Manager stores the latest command timeline received from the operational component. When `loadCommandFile` is true, the Manager uses the uploaded `commandFileContent` and forwards it to the operational component during prep.

The folder is ignored by Git because it contains local run artifacts. If a file name is missing, the Manager uses `latest_commands.txt`.

## Configuration

Edit `config/manager_config.ini` before running on multiple machines.

### General

- `manager_comp_ip` - IP address where components connect back to the Manager
- `manager_PORT` - TCP port for component communication, currently `13020`
- `dataConv_comp_IP` - orbital daemon host
- `operational_comp_IP` - operational daemon host
- `cyber_comp_IP` - cyber daemon host
- `daemon_server_PORT_ENV` - orbital daemon port
- `daemon_server_PORT_OP` - operational daemon port
- `daemon_server_PORT_CYBER` - cyber daemon port

### WebApp

- `WEBAPP_COM.webapp_com_PORT` - WebSocket port, currently `8765`
- `WEBAPP_COM.webapp_com_PORT_ADRESS` - documented WebSocket URL

The WebSocket handler currently binds directly to `localhost:8765`, so changing the config alone will not move the listener without a matching code update.

### MongoDB

- `MONGO_CONFIG.mongo_client`
- `MONGO_CONFIG.db`
- `MONGO_CONFIG.collection`
- `MONGO_CONFIG.isWritingToMONGO`

When Mongo writing is disabled, Manager still runs and streams updates to the WebApp.

The WebApp `saveToMongo` checkbox controls Mongo writing for each normal run. Demo mode can still read graph data from MongoDB according to the demo configuration.

### Demo

- `DEMO_VARIABLES.demoGraphsBatchSize`
- `DEMO_VARIABLES.demo_run_id`

Demo mode loads graph data from MongoDB instead of relying only on live COSMOS telemetry.

## Troubleshooting

- Start the three component daemons before starting a simulation from the WebApp.
- If components do not connect back, check `manager_comp_ip`, local firewall rules, and `manager_PORT`.
- If the WebApp cannot connect, verify that `ManagerServer.py` is running and that the browser is using `ws://127.0.0.1:8765`.
- If a simulation never leaves startup, one of the three expected components did not finish its `prep` handshake.
