# Satellite Security Testbed Web Guide

This guide documents the current React WebApp implementation and how it communicates with the Manager.

The frontend project is:

```text
WebApp/TestBedWebApp
```

## Running the WebApp

```bash
cd WebApp/TestBedWebApp
npm install
npm run dev
```

The Vite development server normally serves the app at:

```text
http://localhost:5173
```

The app currently connects to the Manager WebSocket at:

```text
ws://127.0.0.1:8765
```

Start `src/Manager/ManagerServer.py` before starting a live simulation.

## App Routes

Defined in `src/App.jsx`:

| Route | Component | Purpose |
| --- | --- | --- |
| `/` | `SimConfigPage` | Main simulation configuration screen |
| `/SimConfig` | `SimConfigPage` | Same configuration screen |
| `/sim` | `SimPage` | Live simulation screen |

`Home.jsx` exists as a simple/manual test page but is not registered as an active route in the current router.

## Main Screens

### Simulation Configuration

Implemented by:

```text
src/pages/SimConfig.jsx
src/components/SimParamForm/SimParamForm.jsx
src/components/AttackManager/AttackManager.jsx
```

The screen lets the user:

- upload a `.txt` TLE file
- auto-fill start epoch time from the TLE epoch
- set simulation duration in minutes
- set number of simulations
- choose whether the run should be saved to MongoDB
- save the generated operational command file on the Manager computer
- load a saved operational command file through a browser file picker
- add cyber attacks on a visual second-based timeline
- load demo parameters

When the form is submitted, `SimParamForm.action()` stores the values in Redux and redirects to `/Sim`.

### Live Simulation

Implemented by:

```text
src/pages/SimPage/Sim.jsx
```

The screen contains:

- `CommandLogPanel` on the left
- `MiddlePanel` with graph boxes in the center
- `StatusPanel` with map and controls on the right

`StatusPanel` owns the live WebSocket connection used for start, stop, pause, resume, and incoming Manager updates.

## WebSocket Messages Sent to the Manager

Defined in:

```text
src/assets/msgForServer.jsx
```

### Start

Created by `createStartMsg()`:

```json
{
    "stage": "start",
    "type": "request",
    "data": {
      "simDuration": "90",
      "tle": ["name", "line1", "line2"],
      "tleFileName": "example.txt",
      "attacks": [],
      "time": [2026, 1, 1, 0, 0, 0],
      "startEpochTime": 1767225600,
      "night_probability": 100,
      "playbackSpeed": 1,
      "demoMode": 0,
      "saveToMongo": false,
      "saveCommandFile": false,
      "loadCommandFile": false,
      "commandFileName": "latest_commands.txt",
      "commandFileContent": ""
    }
}
```

`simDuration` is sent in minutes from the GUI. The Manager converts it to seconds when preparing the operational component.

Attack schedules created by the current WebApp use seconds:

```json
{
  "name": "CPUHigh",
  "duration": "20,40",
  "occurrence": "90,180",
  "scheduleUnit": "seconds"
}
```

The attack timeline editor displays seconds, stores comma-separated second values, and adds `scheduleUnit: "seconds"` so the cyber scheduler can trigger attacks at second-level precision.

Command-file fields are used only when the operator selects **Save generated file** or **Load saved file** on the configuration screen:

- `saveCommandFile` asks the Manager to store the command timeline generated by the operational component.
- `loadCommandFile` asks the Manager to forward the selected file content to the operational component.
- `commandFileName` is sanitized by the Manager before it is used on disk.
- `commandFileContent` contains the uploaded file text when loading a saved command file.

### Stop, Pause, Resume

```json
{ "stage": "stop", "type": "request", "data": {} }
{ "stage": "pause", "type": "request", "data": {} }
{ "stage": "resume", "type": "request", "data": {} }
```

### Requested Graphs

`setRequestedGraphsData` asks the Manager to stream selected telemetry fields, including EPS, OBC, TPL, and payload fields.

### Attack Factor

`createSetAttackFactorMsg(factor)` sends:

```json
{
  "stage": "setAttackFactor",
  "type": "request",
  "data": {
    "attackFactor": 1.5
  }
}
```

## WebSocket Messages Received from the Manager

`StatusPanel.handleServerMessage()` dispatches incoming messages by shape:

| Message shape | Redux action |
| --- | --- |
| `stage: "simulationComplete"` | `simActions.completeSimulation()` |
| contains `Time` | `satActions.updateSatState()` |
| contains `command` | `graphActions.handleNewCommand()` |
| contains `EPS_BATTERY_TOTAL_VOLTAGE` | `graphActions.handleGraphUpdate()` |

Satellite-state messages update the map. Command messages update the command log. Graph dictionaries update the chart data.

When `simulationComplete` is received, the WebApp resets the live-run state, returns to `/SimConfig`, and shows a closeable completion popup. After the popup is closed, the same WebSocket server can accept a new start message for another simulation.

## Troubleshooting

- If controls are disabled, the WebSocket is probably not open. Start the Manager and refresh the page.
- If no graph data appears, confirm the operational component is sending COSMOS telemetry and that `setRequestedGraphsData` was sent after start.
- If the map does not move, inspect incoming Manager messages and confirm they contain `Time` plus satellite position fields.
- If attack names do not run, confirm the WebApp attack name matches the cyber dispatch branch in `src/cyber/main.py`.
